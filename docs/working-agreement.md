# 進め方の決まり（オーナーからの指示）

この開発で、オーナー（山本）から受けた指示と、決まった進め方のまとめ。新しい会話・新しいセッションの Claude は、作業の前にここと `CLAUDE.md` を読む。経緯は [history.md](history.md)。

## 会話の仕方

- 日本語で、簡潔に。事実と必要なことだけ答える
  - **使う言語は日本語**（10月23日。オーナー：「このcodeの共通ルール、使用言語は日本語」）。返事・確認の問い・ボタン・コミット・PR・ドキュメント・コードのコメントまで、すべて日本語。英語で返した会話があったため、`CLAUDE.md` の冒頭にも書いた
- **結論から書き、端的にまとめる**（10月24日。オーナー：「できるだけ結論から書いて端的にまとめたやつがいい」「あなたの文章を全部読めてるわけじゃない」）。最初の 1〜2 行で結論、続けて要点を数行。表や前提をたくさん並べない。決めてほしいことは 1 つに絞る
- **カードにフレーバーを入れない**（10月23日。オーナー：「金輪際ですがフレーバーは入れないのでカード作成時に入れないでね。約束ね」）。案を出すときもフレーバー案は書かない
- **カードには、カードを成り立たせる文字だけを載せる**（10月24日。オーナー：「カードを成り立たせる上で不要な『文章』『言葉』は全て削除対象」「これがあると楽しいだろうな、みたいな余計な文言は全て不要」「レアリティの高さも関係ありません」）。名前・コスト・攻撃力・体力・★・種類・属性・界隈・効果文・闇堕ちの札だけ。肩書き・フレーバー・通し番号・飾りの文字は、★5 の専用デザインでも載せない（[card-text.md](card-text.md)「カードに載せる文字」。テストで確かめている）
- オーナーに質問しない。分からないところは妥当な前提を置いて進め、置いた前提を書く
- **オーナーの指示と Claude の案を混ぜない**（10月25日。メン地下の強化に、オーナーが外すつもりだった親衛隊が残っていた。[history.md](history.md)「10月25日：メン地下の強化から親衛隊を外す」）
  - ボタンで聞くのは、質問に書いた 1 つのことだけ。ボタンの文に、聞いていない決定（Claude の案）を足さない。足したい案があれば、別に聞く
  - ボタンの文は Claude が書いたもので、オーナーの言葉ではない。記録するときは「オーナー：『…』」と引用せず、「オーナーがボタン『…』で選んだ」と、選んだことだけを書く。Claude の案が選ばれたときは「Claude の案（理由）をオーナーが選んだ」と書く
  - 「A よりも B？」「A を B に」のような入れ替えの話は、A がいた所をすべて B にする（出すものも、効果の対象も）。A を一部に残したいときは、それは Claude の案として分けて出す
  - 「オーナーの言う形にします」と答えたら、その形のとおりに作る。オーナーの形に合わない動き（Claude の案）を同じ案の中に入れない。入れたいなら、オーナーの形とは別の案だと分かるように分けて出す（10月28日。クサハミで「その後は動かさない」と答えながら「破壊されるたび +1」を残していた）
- 指示された手段が目的に対して最適でないと思ったら、実行前に代替案・根拠・トレードオフを短く出す。ただし明示された制約や権限は勝手に変えない
- 正確さや最新の情報が要るときは Web で調べる
- 専門用語（インフラなど）を聞かれたら、概念から図や例えで説明する

## 開発の回し方

- **手元で確かめて溜め、本番へのマージは 1 日 1 回**（10月25日。オーナー：「今後は手元、つまりローカルで打鍵して、開発もある程度溜め込んでおこう。で、1日一回とかキリのいいところで本番マージでOK」）。GitHub Actions の無料の分数（非公開のリポジトリは月 2,000 分）を、10月は 24 日で使い切った（CI 366 回・デプロイ 139 回。CI は 1 回およそ 5 分）
  - 作業はブランチで行い、手元で `pnpm verify`（CI と同じリント・パッケージのビルド・DB のマイグレーション・型・テスト・ビルド。先に `pnpm db:up`）を通す。API の Docker を変えたときは `pnpm verify:image` も
  - 通ったら、`dev` ブランチに取り込む。ブランチは push してよい。作業ごとの PR は作らない（CI が作業ごとに動いて分数を使うため）
  - **本番に出すのは、dev → main の PR を作り、GitHub の CI が通ったらマージする。この流れは外さない**（10月25日。オーナー：「デブからメインでプルリクをマージする形には絶対に戻したくて、なんかそこの開発フローは絶対に外しちゃいけない」）。出すのは、キリのいいところ・オーナーが出先で遊びたいとき（オーナー：「今はまだ本番公開の段階ではなく、多くの調整を素早くやりたいフェーズ」）。PR は `gh pr create --base main --head dev`、マージは `gh pr merge --merge`（マージコミット。squash にすると dev と main の履歴が分かれる）。docs だけの変更ではデプロイは動かない
    - 10月25日の朝に一度「PR を作らず `git push origin dev:main` で出す」形にしたが、これはオーナーの指示ではなく Claude の案だった（オーナーが言ったのは「1日一回とかキリのいいところで本番マージ」まで）。同じ日に PR の形に戻した

  - **リポジトリは 11 月まで公開**（10月25日。オーナー：「11月になったら閉じます」）。公開のあいだは Actions が無料。11 月に非公開に戻したら、月 2,000 分の枠に戻る

  - git のフック（`.githooks/pre-push`。`pnpm install` で有効になる）：`dev` に push できるのは `pnpm verify` を通した版だけ（`scripts/mark-verified.sh` が覚える）。main への push はすべて止める（main には PR のマージでだけ入る）
  - Claude Code のフック（`.claude/settings.json` → `scripts/claude-guard.mjs`）：`--no-verify`、main への push、`dev` → main 以外の PR、CI が通っていない（落ちた・終わっていない）PR のマージを止める。会話が要約されたら、抜けやすい決まり（`scripts/after-compact.md`）を Claude に読ませる

  - ただし、オーナーが「待って」「マージしないで」と言ったもの、見た目や演出でオーナーと詰めている途中のもの（モックで確認中のもの）は、決まってからマージする
  - **公開（周知・11/1 リリース予定）したら、この決まりは終わり**。オーナーの一言でマージする形に戻す
  - 本番を入れ替えるとオンライン対戦が切れる。オーナーや友人が対戦中と分かっているときは出さない。Deploy も `/health` の `liveMatches` が 0 になるまで最長 30 分待つ（[deploy.md](deploy.md)「公開前の守り」）
- 試遊用のアーティファクト（claude.ai の公開ページ）は、画面を変えたら作り直して同じ URL に出す
- ゲームのルールは `packages/game-core` にだけ書き、テストを付ける。画面にルールを書かない
- スマホ（Pixel 8・iPhone）で遊ばれる前提で、縦横の画面で確かめてから出す
- **画面はスマホの縦の形1つだけ**（10月22日。オーナー：「PC 画面のデザインは消そう。スマホのレスポンシブをそのまま PC からのアクセスでも表示する。2つの画面のメンテを避ける目的。どうせスマホアプリ化するので」）。PC やスマホの横持ちでも、縦の画面を中央に置く。横向き・PC 向けの別のレイアウトは作らない
  - **根っこで一括で決めてある**（10月23日。オーナー：「PC ブラウザで、画面全体にかかるモーダルやアニメーションが全画面で表示されておかしい時がある。システムの一番根幹のところで、全ての行動をスマホサイズの縦画面で行うと一括で定義して」）。アプリ全体を画面の枠（`apps/web/src/frame.ts`・`#app-frame`、幅 480px まで）に入れてある
  - スマホの縦（幅 480px まで）では、枠は何もしない（ページのスクロール・全画面の要素・演出の層は、枠を入れる前と同じ）。それより広い画面だけ、枠に transform を持たせ、中の `position: fixed`（モーダル・全画面の演出）が枠いっぱいに収まり、はみ出しは切られる。スクロールは枠の中の `.app-scroll`
  - **スマホの描画の土台は変えない**（10月23日。枠をスマホでも効かせ、演出の層を枠の中へ移したら、スマホで着地の属性の色などの PixiJS の演出が出なくなった）。演出の層（`#fx-layer`・PixiJS の `#fx-stage`）は body の直下に置く。スマホの縦では画面いっぱい。広い画面では、`#fx-layer` は枠の外を CSS で切り、PixiJS の Canvas はそのものを枠の大きさにする（見えない部分に GPU のメモリを使わない。10月23日の軽量化）
  - 新しい全画面の要素は、ふつうに `position: fixed; inset: 0` で書けば、広い画面では枠に収まる。画面座標（getBoundingClientRect・clientX）で置く要素は `#fx-layer`（`game/fx.ts` の layer()）か `.vp-layer` の中に入れる。画面の大きさは `window.innerWidth` ではなく `frameSize()`・`frameRect()` で測る

- **画面から「最新にする」**（10月23日。オーナー：「不具合らしい時にキャッシュを削除する。PWA の場合に画面から再起動やキャッシュ削除ができる動線が必要では」）。上のメニューの「最新にする」で、サービスワーカーとそのキャッシュを消して読み直す（デッキ・ログインは消さない）。不具合の報告を受けたら、まずこれを案内してよい
- **新しい版には黙って切り替える**（10月27日。オーナー：「リリースによりアプリの更新が必要になったとき、毎回最新にするを押してもらうの酷かな」→ Claude の案（版の印を比べて、ホームにいるときに自動で読み直す）をオーナーが選んだ）。本番を入れ替えたら、開いたままの画面も、アプリに戻ってきたとき・ホームに来たときにサーバーの版の印（`version.json`）と比べ、違えばホームにいるときだけ読み直す。対戦・デッキ作り・ガチャの途中は消さない。「新しい版があります・更新する」の帯はやめた（`src/pwa.ts`）

## ゲームの方針

- ライフ 20、ステータスは攻撃力と体力
- **用語は [glossary.md](glossary.md)（ユビキタス言語）だけを使う**（10月24日。オーナー：「投稿とかアイコンって名前にもこだわらない。カードゲーム好きな人に伝わればいい」「代表的なカードゲームから、一番伝わる集約値的なのにしたい」「ユビキタス言語は何にしても真っ先にやりたい。今後のカード作成で強制的に適用して、ユビキタスに沿っていない文章はテストで CI 通さないのがいい」）。効果文は [card-text.md](card-text.md) の文の型で書く。沿っていない効果文・画面の文字はテストで落ちる
- 属性は 炎・推し・水・自然・神 の5つ（10月24日に 炎上・メロい・癒し・草・神 から改名。闇は闇堕ちとぶつかるので使わない）。1枚に1つ（0はニュートラル）。界隈（ミーム・アイドル・配信者・有識者・動物。10月24日〜25日は種族と呼んだ）は属性をまたいで付け、1枚に2つまで（2つは★3以上の少数）。界隈でデッキは縛らず、界隈を参照する効果は自分の側だけ。方針は `docs/design-v6-kaiwai.md`
- **特定の相手への明示的な特攻（○○に強い・弱い）は付けない**。どの相手とも戦えるようにし、相性は各属性の「勝ち方の癖」から自然に出す。並びは 炎上→メロい→神→草→癒し→炎上（炎上はスキャンダルでメロいに強い）
- ★5・★4 は属性の勝ち方を体現する、尖った切り札にする
- **初期リリースは単属性デッキだけ**（10月19日）。構築済みデッキは単属性の 5 つ、デッキの決まりは「属性 1 つ＋共通カード」（CPU 戦・オンライン戦・自分で組むデッキすべて）。5 属性の総当たりで、どの属性も 45〜55% に収める
- **属性は混ぜられるが、単属性が得をする作りにする**（10月19日。初期リリースのあと、2 属性を解禁するときの方針）。選択肢が多いと人は動かないので、実際は単属性が覇権を取りやすく、2 属性はその対策として使える形にする（シャドバも混ざらなかった）
- **方針メモ（まだカードは変えない）**：★5 などの強化の対象は、基本的に自分の属性か界隈に絞る。見直しの候補（★4・★5 で味方全体を強化・回復・すぐ攻撃させるもの）：伝説のコラ画像（全員すぐ攻撃）、生誕祭・アイリ・トレンドメーカー・ワラ（通常と闇堕ち）・ミレイ（味方全体の強化）、ミナモ・ゆるキャラ（味方全体の回復）
- ★5 は手札から普通に出す（推し枠はやめた）。闇堕ちを持つ★5は、破壊されたら次の自分のターンの始めに自動で闇堕ちの姿で出る（コストなし・選ぶ操作なし。出たターンは相手のキャラクターにだけ攻撃できる＝突進）。闇の姿が破壊されたら消える。闇堕ちは★5だけ（普通のカードには配らない）（10月20日。それまでは「オワコンから自分で選んで出す」。経緯は `docs/design-v5.md` と `docs/design-v10-buzz.md`）
- **デッキは 20 枚・同じカードは 2 枚まで・闇堕ちを持つカードは種類を問わず 2 枚まで**（★5 の種類は制限しない）。闇堕ちの回数は決まりにせず、エース 2 枚で「最大 2 回」を感覚で分からせる（10月20日。10月24日に「1 種類まで」→「種類を問わず 2 枚まで」、オーナー：「闇堕ちキャラはキャラ一体ではなく2枚まで」）
- **バズ**：1 試合 2 回、自分のキャラクター 1 体に攻撃力+2・体力+2と突進。盤面を取り返す手段を、突進のカードに頼らずどのデッキも持てるように。シャドバの進化の丸写しにはしない（強化なので晒し状態で消える・プレイヤーの技としてカットインで見せる）。進化は入れない（10月24日に確認）（10月20日）
- 闇堕ちを持つのは各属性 2 人。基本 6〜7 コストで、通常の姿はシンプル、闇の姿を強く（クサハミだけ低コストの例外）
- **数で強くなる効果は、効果が働いたときに一度だけ数えて強化として足し、そのあとは数字を変えない**（10月25日。オーナー：「一回確定した数値っていうのは、一切その場で変動しなかった」「そのカードの効果が発動する前に計算を全て終える」「倒された草を計算した後は、もうそのステータスの方にバラスした後には変えない」「動く変数を持ってなかったイメージ」）。「【場に出たとき】〜の数だけ攻撃力+1」の形にし、数字の元は強化だけにする（強化なので晒し状態・TL浄化で消える）。場にいる間ずっとその場で数える形は、数が減ることもあるもの（自分の場のほかの〇〇1体につき、など）に限る。きっかけはクサハミの攻撃力が、草が破壊されるたびに黙って 1 つずつ上がっていたこと
  - 10月25日の作り直しでは、クサハミに「自分の草が破壊されるたび、攻撃力+1」を残していた。これはオーナーの言葉ではなく、その会話の Claude の案で、場に出たあとも攻撃力が増え続けた。10月28日に外した（[history.md](history.md)「10月28日：クサハミの攻撃力を、場に出たときに確定させる」）
- ゲームの仕組みはシャドバなど既存のゲームそのものにしない（進化の丸写しは不可）
- 実在の人物は描かない（例：野獣先輩は不可）
- 次のバランス調整は、先読みする CPU（`planTurnSearch`）同士の結果を基準にする（`docs/rules.md`）

## 演出・カードデザインの決まり

- **画面の配色は ①ソーダ（白 × 水色）**（10月26日。オーナー：「黒基調で黄色はあまりカードゲームのUIではない」「令和ぽいというかペールカラーとか透ける感じの色合い」「ポケポケのUIとか」「任天堂系」→ モックの 3 案から「①にしよう」「このカラーデザインで他のすべての画面も作って」）。色の元は `apps/web/src/styles/app.css` の `:root`。地は白 × 水色、面は白いすりガラス、文字は濃い紺、主のボタンは水色のグラデーションに白い字。新しい画面もこの色の元から作り、色を直に書き足さない
  - 対戦の盤面の地だけは、パレットの濃い青（`.play-full`）。光を足す演出（加算合成）が明るい地では見えなくなるため。盤面の上の帯・ボタンは白いすりガラス
  - **部品の決まり**（10月26日。オーナー：「全体で使っていいカラートーンやスマホサイズのWebサービスで使用できるUI、色合い、透け具合などを再考して」→ モックで見せて「全体感差し替えよう」）。元は `app.css` の `:root`
    - 主の色は水色 1 つ。グラデーションは 1 画面に 1 つの主のボタンだけ。ほかのボタンは白いすりガラス（`.btn.ghost`）か字だけ（`.btn.text`）
    - すりガラスは 3 段（`.g1` 絵の上の札・戻るボタン / `.g2` パネル・行 / `.g3` 小窓・下の台）。影は 1 色で 3 段（`--sh-1`〜`--sh-3`）
    - 属性の色は属性の丸（`.at`）だけ。金・銀・銅は★と順位の 1〜3 だけ。うまくいった・だめの色（`--ok`・`--ng`）は文字と小さな点だけ
    - 選んだ絞り込みの札は濃い紺、選んだ切り替えは白い丸

## 作業する場所

10月23日から、開発は **Claude デスクトップアプリの「Code」タブ**で行う（オーナー：「同じ Claude デスクトップアプリの『Code』タブに開発を移す」）。移した理由は、チャットだと 1 回の依頼をまとめて処理して途中が見えず、並行して頼みにくいため。Code タブは進み方がそのまま流れて見え、セッションを並べて同時に走らせられる。アーティファクト・`/design`（Claude Design のアートボード）・アプリのプレビュー・Claude in Chrome も使える。

| 依頼 | 場所 |
|---|---|
| 実装・バグ修正・演出・カード追加・バランスのシミュレーション | Code タブ（このリポジトリ） |
| 仕様・ルール・バランス方針の相談、試遊の要望の整理 | claude.ai のプロジェクトのチャット（ナレッジに docs がある） |

- Code タブの Claude は、claude.ai のプロジェクトのメモリーを読めない。**オーナーから受けた指示・決まりは、すべてこのファイルか docs に書く**（メモリーだけに置かない）
- **並行で頼むとき**：セッションごとに作業場所を分ける（Git の worktree。同じリポジトリの「作業机」を別々に持つので、書きかけが混ざらない）。それぞれブランチで作り、手元で `pnpm verify` を通してから `dev` に取り込む（PR は 1 日 1 回の `dev` → main だけ）。同じカード・同じ演出は同じセッションで続ける。`docs/history.md` はほぼ毎回触るので、後から取り込む側が `dev` を取り込んでから入れる
- **ブラウザ（Claude in Chrome）で画面を確かめる作業は、1 つのセッションに寄せる**。複数のセッションが同じ Chrome を同時に動かすと取り合いになる
- 画面の確認は、Code タブのプレビュー（手元で動かしたアプリを埋め込みのブラウザで開く）か Claude in Chrome。スマホの縦（幅 390 前後）で見る
- 記憶：決まりはこのファイルと `CLAUDE.md`、経緯は `history.md`。Claude Code が自分で付けるメモ（auto memory）は補助で、そこにしかない決まりを作らない
