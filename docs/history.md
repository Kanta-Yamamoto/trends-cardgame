## 10月19日：iPhone のアプリで対戦画面が拡大縮小されるのを止める

- iPhone のホーム画面アプリで、対戦画面が全画面に広がらなかったり極端に小さくなったりした（オーナーの Pixel 8 では起きない）。原因は、連打がダブルタップ拡大・2本指がピンチ拡大になることと、舞台の大きさを `window.innerWidth/innerHeight`（iOS では拡大後に見えている範囲）で測っていたこと。向きを変えた直後に倍率が 1 でなくなることもある
- 対策（A 案）：全体に `touch-action: manipulation`、ピンチは `gesturestart` と2本指の touch イベントを止める（対戦中はいつでも、ホーム画面アプリでは全画面）、舞台は拡大の影響を受けない大きさ（visualViewport × 倍率）で測る、向きを変えたあと倍率が 1 でなければ viewport を当て直す、メタに `maximum-scale=1, user-scalable=no, shrink-to-fit=no`
- 見送った案：スマホの対戦画面を横固定にする（iOS Safari は `screen.orientation.lock()` 非対応なので、CSS で 90° 回す方式になる。A を出してから iPhone で様子を見て判断）、Capacitor でネイティブ化（配布に Apple Developer Program が要る）

## 10月19日：凸を足し、叩きを外し、ガードを減らす（ルールの見直し）

- オーナー：「叩きは弱いので炎上のメインの性能にしない。シャドバの突進（場に出たターンに相手のフォロワーだけ攻撃できる）にあたる **凸** を入れる。凸にステータス強化は付かない。闇堕ちは無条件で凸。ガードは無条件で相手に戦いを強いるので持ち主を減らす。全員への進化権のような付与はなし（闇堕ちがメインテーマなので、進化と同等のものは置かない）」。一度「話題力 1 を払って +1/+1 と凸（バズ）」も作ったが、「言い換えの言葉が増えると混乱する。凸(1) も分からない」で取りやめ、普通の効果文「凸で攻撃したとき、攻撃力+N・体力+N」に置き換えた

## 10月20日：差し替えた絵が届かない

- オーナー：「破壊された後の消えるモーションが黒で統一されておらず、白色の変なエフェクトが残っている場合がある」「ブラウザでプレイ中に、黒く画面が処理落ちする場合がある。極端に負荷をかけるような状況になっていないかの調査と、一才ユーザー体験を変えないまま、軽量化できる部分を軽量化する」

  - あわせて、カードの幅が 0 のとき（盤面の組み直しの瞬間など）に消え方が途中で失敗すると、片付けと「描画を止める」が呼ばれず、演出の舞台が画面いっぱいの大きさで毎フレーム描き続ける穴があった。失敗しても必ず片付けて止める。大きさが 0 なら溶かさずに消すだけ（ほかの演出には前から同じ守りがあった）
- 重いところ（見つけたもの）：
  1. 演出の舞台（PixiJS の Canvas）を、PC ではブラウザの画面いっぱい（2880×1626）に作っていた。見えるのは幅 480 の枠だけで、残りは CSS で切っていた。アンチエイリアス付きの描画バッファは、この大きさで 100MB 前後。外部モニター（2560×1440）なら 300MB を超える。内蔵 GPU（メモリを本体と共有）では、画面が黒くなる・止まる原因になりうる

  3. 演出の描き方（シェーダー）は最初に使うときに組み立てるので、最初の攻撃・最初の破壊で画面が止まっていた（測ったときは最大 1.27 秒）
- 直したこと（見た目・動きは変えない）：
  1. PC など広い画面では、Canvas そのものを枠の大きさ（960×1626）にする（`fx/stage.ts`。描く位置は枠の左上の分だけずらすので、演出の座標の計算はそのまま）。スマホの縦は前と同じく画面いっぱい（スマホの描画の土台は変えない）
  2. 舞台の用意を、デッキを選んでいる間か、VS の演出が終わってから、手が空いたときに行う（`fx/warm.ts`）
  3. 用意したら、演出で使う描き方を、画面に出ない小さな板に 1 度だけ描いて組み立てておく
- 確かめたこと：最初の破壊を含む攻撃 15 回で、50ms を超えるフレームが 9 回（最大 1.27 秒）→ 0 回（すべて 17ms）。デッキを選んでから VS の間のロングタスクは合計 0.45 秒前後 → 0.07〜0.23 秒（残りは開発版の React の描画で、本番の版ではもっと短い）。スマホの縦（390×844）の Canvas は前と同じ 780×1688。消え方のコマ送りで、白いもやが出ないこと、PC でも溶ける板がカードの位置にぴったり重なることを見た

## 10月24日：炎属性をアグロに作り直す

## 10月24日：強化は一度上がったら下がらない

- オーナー：「一回された強化は戻らないはず。場にいるアイドルの分攻撃力をプラスするキャラが、アイドルが離れたら攻撃力が下がっていた」「一回行われた強化は戻らないし、今後も場を見て数値が変動することはないようにしたい」
- 代表的なカードゲームには両方ある（ハースストーンの雄叫び・シャドバのファンファーレは残る、ハースストーンのオールド・マークアイや MTG のロード系は数え直す）。このゲームは「残る」に統一した。強化が消えるのは晒し状態（炎）と TL浄化（水）だけ
- 数え直していた 3 枚を、出たときに数えて強化する形にした：伝説のコラ画像・ワラ・コラボ配信。ワラは草を出してから数える。出たあとに仲間が増えても伸びない（少し弱くなる）
- 場の数で攻撃力が変わる効果が入ったら落ちるテストを足した。コストが場の数で変わるカードは無い（ゆるキャラは「回復した回数」）

## 10月24日：神属性を作り直す

- 五角形を 10月の作り（炎 → 推し → 神 → 自然 → 水 → 炎）に戻した。design-mainline.md の表の「神は推しに強い」と食い違っていた

- CPU どうしで 60 戦 52 勝と強すぎる。ネ申を抜いても 40 戦 34 勝で、ガードの壁が原因
- 強すぎたので、雑学博士のガードを外し、手札でいちばんコストが高い神属性のカードのコストを 1 下げる役にした（オーナー：「神の特徴はガードと確定除去とコスト低下」「どっちかをガードを抜いて、コスト削減にしよう」）。60 戦 47 勝で、まだ強い

- ベテラン解説者の軽減を 2 → 1 にした（オーナー：「-2 じゃなくて -1 にしてあげて」）。60 戦 41 勝のままで、勝率は変わらなかった
- ミコトを 1/5 に下げても変わらず（42 勝）。1 種類ずつ抜いて比べると、専門家と序盤の除去（ファクトチェッカー・Wiki編集者）がいちばん効いていた。陰謀論者の特殊勝利は 40 戦中 2 回だけで、強いのは固い壁が戻ってくること。専門家を 3/4（陰謀論者 4/3）にして 60 戦 38 勝（オーナー：「じゃあ、これは3、4にするか」）
- ファクトチェッカー（1 ダメージ）は神のコンセプト（ガード・確定除去・コスト低下）に合わないので、1 コスト 0/2・ガードの小さい壁にした（オーナー：「神って1ダメージ与えるのってコンセプトじゃない気がする」）。シャドバのビショップの安いカード（小さい守護・カウントダウンのアミュレット）を参考に話し、アミュレットにあたる置物は第 2 弾で「トレンド」として入れる案に。60 戦 37 勝（今の水に 9 勝。水を除くと 56%）

## 10月24日：水属性を作り直す・トークンの決まりを変える

## 10月25日：自然属性を作り直す

## 10月25日：CPU のバズの使い方と、便乗

- オーナー：「自分のデッキを握った時に、不用意にバズを使わず、相手のキャラクターの除去のために、3〜4以上の攻撃を持つ相手を自分のバズによって自分を残しながら倒せる時に積極的に使うようにして」「体力、盤面的に有利な場合には積極的に顔を殴る」
- 「除去を優先し、残りは 6 ターン目から盤面・リーサルに使う」形にすると、前の CPU に 34% しか勝てなかった（各 196 戦）。除去になるまで取っておく形はどれも 32〜37%。自分の 5 ターン目までに、相手に攻撃力 3 以上のキャラクターがいたのは 15% のターンだけで、その場面では 7 割で除去に使っていた。バズの +2/+2 は消えずに残るので、早く使うほど得をする。取っておくと負けるのは炎・水・推しなどデッキを問わず同じで、アグロが止められていない証拠ではない
- オーナー：「シャドバの進化の使い方と考えると、進化を先に使えるのは後攻で4ターン目から、先攻は5ターン目から。もしかしてそこのせい？」→ 時期をそろえても、取っておく CPU は 32% のまま。先攻の勝率（新しい CPU どうし・各 1176 戦）は、今の決まり 51%、シャドバの時期・後攻のコスト+1あり 47%、シャドバの時期・コスト+1なし 55%。オーナー：「無理に先行後攻の状況は変えなくていいや」で、今の決まりのまま
- オーナー：「シャドバは、進化によって効果が変わる場合が多いから、相手の場の状況によって進化を切るか切らないかが影響される」「今の突進付与システムだと、全くいつ切るかについて影響する要素が少なすぎる」「これは進化をまねないぞと思ったのに、とんだ失態ですなぁ」
- CPU は、使えるようになったターンから盤面の取り合いに使う形にした：除去・とどめ・プレイヤーを殴れるキャラクター・出したばかりのキャラクターにだけ試し、攻撃し終えた・眠り状態のキャラクターには使わない。前の CPU と互角（46%）。有利なら相手のライフを削る点を重く見る構えも入れた（勝率はほとんど変わらない）
- 相手のバズに反応する「フィールド」は新しいカードの種類になるので、第 2 弾のトレンドで考える。「バズしたキャラクターから攻撃されない」は、付けるならほかの低い属性に（決めていない）
- 便乗（キーワード）：自分か相手がバズを使うたび、攻撃力+1・体力+1。歌い手（4 コスト 3/4）とバーチャルアイドル（2 コスト 1/3）に付けた。詳しくは [design-oshi.md](design-oshi.md)「便乗」
- CPU どうしの総当たり（各デッキと 20 戦・計 420 戦。水は作り直し前）：便乗を入れる前 → 入れたあとで、推し 39% → 43%（誤差は ±9% ほど）。ほかは水 66→63%・クサハミ 64→63%・神 57→55%・運営 57→57%・炎 35→39%・全体強化 32→29%。バズは 1 人 1 試合 2.0 回


## 10月25日：ネ申と神のトークンの絵

- オーナーが描いたネ申・裁きの雷・盾・天罰の絵を取り込んだ（オーナー：「これ神の画像」「これが、神のトークン。雷、盾、後一個なんでもいいやつ」）。天罰には地球の模型を指先で弾く絵を当てた。巨大な神が雲と溶け合っていて切り抜けないので、4枚とも背景の絵だけ（切り抜きは無い）

## 10月25日：水の作り直しを main に合わせる

- 水の作り直し（#138）のあとに、自然の作り直しと CPU のバズの直しが入ったので、食い違いを直した。手札から出す処理は両方の変更（リスナーのガードを先に決める・伝説のコラ画像の「先に出した」数）を合わせた

## 10月25日：GitHub Actions の分数を使い切った・本番へのマージは 1 日 1 回に

- #140 のマージのあと、CI が「支払いが失敗したか、上限額を上げる必要がある」で動かなくなった。非公開のリポジトリの無料の分数（月 2,000 分）を使い切った。10月は CI 366 回・デプロイ 139 回で、CI は 1 回およそ 5 分（ジョブごとに分を切り上げて数える）
- 水の作り直し（#138）は、手元でテスト・リント・型が通っていたので、オーナーの指示で CI なしでマージした。CI が動かないので、#140 と #138 は本番に出ていない
- リポジトリを公開にすれば Actions は無料だが、公開中にコピーされたもの（フォーク・自動の保存）は非公開に戻しても消せず、絵と設計がずっと見えるので見送った
- オーナー：「今後は手元、つまりローカルで打鍵して、開発もある程度溜め込んでおこう。で、1日一回とかキリのいいところで本番マージでOK」。手元で `pnpm verify` を通して `dev` に溜め、1 日 1 回 `dev` → main の PR を作る。docs だけの変更では CI を回さない（`paths-ignore`。ci.yml を変えるには GitHub のログインに `workflow` の権限が要り、オーナーの操作待ち）


## 10月25日：CI は手元に寄せ、本番にはいつでも出せるように・決まりをフックで守らせる

- オーナー：「今はまだ本番公開の段階ではなく、多くの調整を素早くやりたいフェーズ」「本来は俺が出先でプレイしたいってだけで先行デプロイしちゃった」。1 日 1 回の PR はやめ、手元で `pnpm verify` を通した `dev` を `git push origin dev:main` で出す。動くのはデプロイだけ（1 回およそ 3 分）
