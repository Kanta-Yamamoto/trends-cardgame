# CPU 対戦の記録

オーナーと CPU の対戦を一手ずつ残し、Claude が読み返して CPU を強くするための記録。

## 目的（10月26日、オーナー）

- **最終の目的はカードのバランス調整**。そのために強い CPU を作る。CPU は、オーナーと戦った記録で鍛える（オーナー：「この対戦では、カードのバランス調整が最終目的、そのためにはつよいCPUを作るべき」「そのためには俺と戦って最適化されるべき」）
- **サブの目標：CPU 同士で勝率の低いデッキが、本当に弱いのか、CPU が使いこなせていないだけなのかを分ける**（10月26日。オーナー：「コンピューター同士の対戦で、著しく、勝率が低かった属性でも、人間が操作すると、勝率が CPU に対して5分とかになる可能性がある」「そこら辺っていうのを取りたい」）。デッキごとに、CPU 同士での勝率・オーナーがそのデッキを使ったときの CPU への勝率・CPU がそのデッキを使ったときのオーナーへの勝率を並べる。オーナーの腕前は CPU と違うので、オーナーの全デッキ平均と比べて、そのデッキだけ上がる（CPU の使い方が下手 → CPU を直す）か、上がらない（デッキが弱い → カードを調整する）かを見る
- 分析は、ゲームに AI を組み込まず、Claude が記録を読んで行う（オーナー：「AIはそれこそ、あなたがDBを読み取って解析でいいか。わざわざシステムに導入せずとも」）。分かったことは CPU の点数の付け方（`packages/game-core/src/search.ts`）の調整としてコードに入れ、CPU 同士の総当たりで強くなったかを確かめてから出す

## 何を残すか

CPU 対戦（`/play`）が終わったとき（決着・降参）と、途中でやめたとき（戻る・新しい対戦・オンライン対戦へ・画面を閉じる）に、1 試合を 1 件として本番の DB（`cpu_games`）に送る。一手も進んでいない対戦は送らない。

| 中身 | 何のため |
| --- | --- |
| 最初の盤面（`initial`）と、起きた順の操作（`moves`。始めからの経過ミリ秒つき） | 最初から1手ずつ再生できる（乱数も盤面の中にあるので同じになる。`replayRecord`）。人がどこで考え込んだかも分かる |
| CPU が1ターンごとに考えた中身（`thoughts`）：比べた候補の上位 5 つ（手・そのターンの終わりの点数・相手の殴り返しまで読んだ点数）と、選んだ候補 | CPU がなぜその手を選んだか、ほかに何を考えていたか |
| 両者のデッキ（構築済みの ID か "custom:…" と中身）・先攻・乱数の種 | デッキごとの勝ち負け |
| 決着（勝った側・ターン数） | |
| カードのデータの印（`cards`。コスト・数値・効果から作る短い文字。名前・絵では変わらない） | カードを調整した前と後の記録を分ける。今のカードと印が違う記録は、そのままでは再生できない |
| 端末の印（`client`。ブラウザに置く乱数の ID） | 同じ人の対戦をまとめて見る |

名前・メール・アカウントは残さない。記録の型は `packages/game-core/src/record.ts`（`CpuGameRecord`）、送るのは `apps/web/src/game/cpuLog.ts`、受け取りと取り出しは `apps/api/src/logs/`（`POST`・`GET /logs/cpu-games`）。公開前は、招待リンクの守りの内側にある（合言葉を知っている人だけが読める）。

## 取り出して見る

```sh
pnpm build                                  # パッケージをビルドしておく
TRENDS_INVITE=合言葉 pnpm logs:cpu fetch     # 前回の続きから取り出して .claude/cpu-logs/ に保存（Git には入らない）
pnpm logs:cpu summary                       # 一覧と、デッキの組み合わせごとの勝ち負け・再生できるか
```

手元の API から取るときは `TRENDS_URL=http://localhost:3001`（合言葉は要らない）。

## 分析の回し方

オーナーが何戦か遊んだら「分析して」と言う。Claude は記録を取り出し、負け方の型・CPU の悪手（人が勝った試合で、CPU が選んだ候補と人の手を比べる）を洗い出して、CPU の点数の付け方を直し、CPU 同士の総当たりで確かめてから出す。直したことと、その理由は [history.md](history.md) に残す。

## 分析の記録

### 10月26日：6戦（オーナー 3 勝・CPU 3 勝）

- **勝ち逃しは無かった**：CPU の毎ターンを、時間と手数を10倍近くにして考え直しても、そのターンで勝てたのに逃した場面は無かった
- **考える量は足りていた**：1ターンに試した手は多くて 1034（上限 8000）。時間切れで弱くなってはいない
- **弱点：比べる候補が、置いた場所だけ違う同じ手で埋まっていた**。CPU が最後に比べた上位の候補のうち、中身が違うのは 43% だけ（のべ 274 のうち 118）。2枚出すと、場所（センター・左端・右端）と出す順の組み合わせで同じ中身の盤面がいくつもでき、本当に別の手（プレイヤーを殴る・残す など）が比べる前に落ちていた
  - 直した：途中で残す候補と最後に比べる候補を選ぶとき、中身が同じ盤面は点数のいちばん高い1つだけにする（`search.ts` の `distinctBest`）
  - 確かめ：直した CPU と直す前の CPU を、全49のデッキの組み合わせ・先後入れ替えで 3920 戦 → 直した側の勝率 51.9%（2回に分けて、どちらも 51.9%）
- **CPU の負け方（カードの強さの話）**
  - 3戦目：オーナーの毒草喰らいのクサハミが、攻撃力 15・速攻で闇堕ちして、CPU のライフを 17 → 2 にした。CPU は前のターンにこの危なさを読めていたが（読みの点数 -29.6）、どの手でも防げなかった
  - 4戦目：神コントロール（CPU）が、炎アグロに序盤から削られ（15 ターン目にライフ 3）、ネ申を出せたのは 17 ターン目
  - 6戦目：オーナーの神コントロールがネ申を出したターンに、天罰と裁きの雷で CPU（水コントロール）の場が消え、ライフ 20 → 11。そこから押し返せなかった
  - 1戦目：オーナーのライフが 1 のまま 12 ターン続いたのは、CPU（水コントロール）の手札が尽きて毎ターン引いた1枚だけだったため（判断の誤りではない）
- **CPU どうしの総当たりで見えたデッキの差**（直した CPU を使ったときの勝率。相手のデッキは全部を同じ数ずつ）：自然・クサハミ 75%・神コントロール 68%・炎アグロ 51%・運営ミッドレンジ 51%・水コントロール 46%・自然・全体強化 37%・推しミッドレンジ 35%。人との対戦の数が増えたら、これと突き合わせてバランス調整の候補にする
